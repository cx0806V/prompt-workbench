# 这个技术选型，帮我做决定

- **id**：`tech-select`
- **分类**：开发
- **什么时候用**：在两个库/框架/方案之间纠结，怕选了之后回不了头。
- **关键词**：选型、技术选型、对比、选哪个、框架、数据库、adr、纠结

## 问题清单（按顺序，一次只问一个）

1. `decision`（必填）：要决定什么？一句话，比如「前端框架选 Vue 还是 React」。
   - 为什么问：把纠结写成选择题，才有可能做决定。
   - 示例回答：后端选 Cloudflare D1 还是 Supabase
2. `options`（必填）：候选方案有哪些？包括你现在已有的技术栈。
   - 为什么问：「保持现状」也是一个选项，常常最优。
   - 示例回答：A. D1（已绑定 Workers）B. Supabase（免费额度大）C. 不做后端
3. `criteria`（必填）：最重要的 3 个标准是什么？（成本 / 学习成本 / 生态 / 性能 / 锁定风险）
   - 为什么问：标准不清，对比表就没有意义。
   - 示例回答：免费、我能学得会、以后换起来不痛苦
4. `constraint`（可选）：有没有硬约束？必须用某个平台、不能花钱、时间只有几天。
   - 为什么问：硬约束常常直接排除一半选项。
   - 示例回答：不能花钱，一周内要能上线

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位技术负责人。请按 ADR（架构决策记录）的格式帮我做决定，不要和稀泥。

## 要决定的问题
{{decision}}

## 候选方案
{{options}}

## 我的判断标准
{{criteria}}

## 硬约束
{{constraint}}

## 输出要求
1. **决策建议**：先给结论（选哪个 + 一句话理由）。
2. **对比表**：行是标准，列是候选方案，单元格写具体事实（价格、限额、学习时间），不确定的标「待核实」。
3. **决策依据**：为什么这个标准权重最高，用我的实际约束解释。
4. **后果**：选它之后，我会失去什么（锁定、迁移成本、维护负担）。
5. **放弃的方案**：写清为什么不选，以及什么情况下应该重新考虑它。
6. **验证方式**：在正式采用前，我用一天时间能做的验证试验是什么。

## 禁止
- 不要编造价格、限额、性能数字；不确定就标「待核实」。
- 不要说「都可以，看需求」——必须给推荐。
````
