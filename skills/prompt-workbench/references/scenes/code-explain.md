# 让 AI 把这段代码讲清楚

- **id**：`code-explain`
- **分类**：开发
- **什么时候用**：接手别人的代码、看开源项目源码、或者自己以前写的代码看不懂了。
- **关键词**：看懂、解释、源码、reading、讲解、学习、调用链、看不懂

## 问题清单（按顺序，一次只问一个）

1. `code`（必填）：把要看的代码贴上来（或给仓库路径 + 入口文件）。
   - 为什么问：讲解必须基于真实代码，不是基于名字猜。
   - 示例回答：贴出 src/render.js 全文，约 120 行
2. `purpose`（必填）：你为什么读它？要改它、要学它的写法、还是要找 bug。
   - 为什么问：目的不同，讲解的深度和侧重点完全不同。
   - 示例回答：我要在它上面加一个功能，得先搞清数据怎么流动
3. `level`（必填）：要讲到什么程度？一句话概括 / 逐段讲 / 讲到能自己改。
   - 为什么问：「讲清楚」没有标准，必须自己定。
   - 示例回答：讲到我能自己改，关键数据结构要讲明白
4. `known`（可选）：你已经看懂哪部分了？哪里开始卡住？
   - 为什么问：从卡点开始讲，比从第一行讲起省一半时间。
   - 示例回答：前面配置能看懂，从 handleSubmit 开始不知道数据去哪了

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位善于讲清复杂代码的工程师。讲解要给出证据，不要凭函数名猜。

## 代码
{{code}}

## 我读它的目的
{{purpose}}

## 需要讲到的深度
{{level}}

## 我已经看懂/卡在哪
{{known}}

## 输出要求
1. **一句话结论**：这段代码整体在干什么。
2. **调用链**：从入口到出口，按顺序列出关键函数，每个函数一句话说明它负责什么。
3. **关键数据结构**：列出最重要的 1–3 个对象/变量，说明它的字段从哪来、到哪去。
4. **设计取舍**：这段代码为什么这样组织，有没有明显的替代方案。
5. **可改进点**：只列真正影响维护的 1–2 条。
6. 每一节都用「结论先行 + 代码行号佐证」的写法；如果代码里看不出来，明确说「这里看不出来，需要看 X」。

## 禁止
- 不要逐行翻译代码。
- 不要把没在代码里出现的行为说成事实。
````
