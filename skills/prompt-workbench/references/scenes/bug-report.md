# 把这个 bug 写成能复现的 issue

- **id**：`bug-report`
- **分类**：开发
- **什么时候用**：要提 issue / 向别人报障 / 交给 AI 修，但你现在只会说「它坏了」。
- **关键词**：issue、bug报告、复现、提issue、报障、反馈、提交

## 问题清单（按顺序，一次只问一个）

1. `problem`（必填）：哪里坏了？用一句话说，不要带情绪。
   - 为什么问：一句话说清的 bug，才有可能被快速修。
   - 示例回答：点保存后页面刷新，数据没存上
2. `steps`（必填）：复现步骤？按顺序写，一步一个动作。
   - 为什么问：能按步骤复现，是 bug 报告的第一价值。
   - 示例回答：1 打开设置页 2 改昵称 3 点保存
3. `expect`（必填）：预期是什么？实际是什么？两句话。
   - 为什么问：没有对照，维护者无法判断是 bug 还是设计如此。
   - 示例回答：预期昵称被保存并显示；实际刷新后变回旧昵称
4. `env`（必填）：环境和版本？系统 / 浏览器 / 应用版本 / 提交号。
   - 为什么问：同一 bug 在不同版本原因不同。
   - 示例回答：Windows 11 / Edge 141 / 版本 v0.3 / commit ae8093b
5. `evidence`（可选）：有截图、日志、报错原文吗？直接贴。
   - 为什么问：证据能省掉一整轮来回追问。
   - 示例回答：控制台有 POST /api/save 500，附截图

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位开源项目维护者。请把我下面的描述整理成一份高质量的 issue，我可以直接复制提交。

## 我遇到的现象
{{problem}}

## 复现步骤
{{steps}}

## 预期 vs 实际
{{expect}}

## 环境
{{env}}

## 证据
{{evidence}}

## 输出要求
1. **标题**：一句话，包含「在什么条件下 / 什么坏了」，不要用「求助」「急」。
2. 按这个结构输出：环境 / 复现步骤（编号，每步一个动作）/ 预期行为 / 实际行为 / 证据 / 影响范围（多少人、什么场景受影响）。
3. 最后加一段「我猜测的原因」——标成**猜测**，不要说得像结论。
4. 去掉所有情绪化表达（「崩溃了」「气死」），只留可验证的事实。

## 禁止
- 不要编造我没有提供的日志或版本号。
- 不要替我把「猜测」写成「已知」。
````

## 交付要求

````text
## 通用交付规则（自动附加，优先级高于上面的表述）
- 如果我要的是「一个结果」（代码、程序、文案、方案、清单、报告）：**先给一版能直接用的最小版本**；缺的参数用默认假设填上并标注「假设」，不要因为信息不全就只问不产出。
- 如果我要的是「改我现有的仓库/文件/系统」：先列改动清单等我确认，再动手。
- 需要我补充的信息最多 3 条，放在结果之后，不要放在最前面。
````
