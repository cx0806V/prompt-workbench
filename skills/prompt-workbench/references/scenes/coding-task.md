# 把任务变成 AI 能执行的开发任务

- **id**：`coding-task`
- **分类**：开发
- **什么时候用**：要把一个开发任务交给 AI 写代码，但说太粗它乱改、说太细自己又费劲。
- **关键词**：开发、写代码、重构、修 bug、仓库、实现、任务、技术

## 问题清单（按顺序，一次只问一个）

1. `task`（必填）：要做什么？一句话说清要改什么、加什么。
   - 为什么问：AI 最怕的不是任务难，是任务边界不清。
   - 示例回答：给项目加一个导出 CSV 的按钮 / 把登录逻辑从 session 改成 token
2. `context`（必填）：技术栈和现有结构是什么？关键文件/目录叫什么？
   - 为什么问：不给上下文，AI 会自己发明一套结构。
   - 示例回答：Node + Express，路由在 routes/，前端是原生 JS
3. `done`（必填）：怎么算做完了？列出可验证的检查项（能跑什么命令、点什么按钮）。
   - 为什么问：这是唯一能防止 AI「说完成了其实没完成」的东西。
   - 示例回答：npm test 全绿 / 点导出按钮能下载到 CSV，中文不乱码
4. `noGo`（必填）：哪些东西不能碰？不能改的文件、必须保持兼容的行为、不能加的依赖。
   - 为什么问：不写禁区，AI 会顺手重构你没让它动的地方。
   - 示例回答：不要改数据库表结构 / 不要新增依赖
5. `style`（可选）：有没有必须遵守的代码风格或约定？
   - 为什么问：风格不一致是后续维护成本的主要来源。
   - 示例回答：用 ESM，不要 CommonJS / 函数不超过 50 行

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位严谨的高级工程师。请先理解任务，再按下面的约束执行；不确定的地方先问我，不要猜。

## 任务
{{task}}

## 现有环境
{{context}}

## 完成标准（必须逐条验证）
{{done}}

## 禁区（不能改动的地方）
{{noGo}}

## 代码约定
{{style}}

## 执行规则
1. 先复述你理解的任务，并列出你打算改动的文件清单，等我确认后再动手。
2. 只改清单内的文件；需要改清单外的东西，先说明原因并征求同意。
3. 每完成一步，报告「当前状态 + 下一步」。
4. 完成后逐条对照「完成标准」自检，给出每一条的验证方式。
5. 不要为了「顺便优化」重构无关代码。
````
