# 帮我做一次安全自查

- **id**：`security-check`
- **分类**：开发
- **什么时候用**：项目要公开、要给同学/客户用、或者代码里有 key 和用户数据。
- **关键词**：安全、自查、泄露、key、权限、注入、隐私、xss

## 问题清单（按顺序，一次只问一个）

1. `target`（必填）：要自查什么？代码 / 部署配置 / 接口 / 依赖 / key 管理。
   - 为什么问：安全范围太大，必须先圈定。
   - 示例回答：一个要公开的纯前端网页 + 一个 Cloudflare Worker
2. `exposure`（必填）：谁会访问它？公开互联网 / 班内 / 只有自己。会不会被爬、被刷。
   - 为什么问：公开程度决定风险等级。
   - 示例回答：会发到群里，几百人可能点，也可能被搜索引擎抓到
3. `data`（必填）：有什么敏感数据？key、token、手机号、用户内容。存在哪。
   - 为什么问：数据在哪，泄露面就在哪。
   - 示例回答：前端不能有 key；用户填的内容只存在 localStorage
4. `stack`（可选）：技术栈和部署方式，以及最近改过什么。
   - 为什么问：「最近改过什么」是漏洞最常见的入口。
   - 示例回答：纯前端 + Worker 代理，最近加了 API 调用

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位应用安全审计员。给我按风险排序的清单，每一项都要能验证，不要说「注意安全」。

## 自查范围
{{target}}

## 暴露面
{{exposure}}

## 敏感数据
{{data}}

## 技术栈
{{stack}}

## 输出要求
1. **必须立刻做的 3 件事**：如果不做，明天就可能出事的。
2. 风险清单，按 🔴高 / 🟡中 / ⚪低 分组，每条包含：
   - 风险点（具体到文件/配置/接口）
   - 攻击者会怎么利用（一句话）
   - **验证方法**（我怎么自己确认它是不是真的有问题）
   - 修复方式（最小改动）
3. 最后给「这次不用管」的清单，说明为什么风险可接受。
4. 涉及前端 key、CORS、注入、依赖漏洞这几类时必须点名检查，如果没有就写「未发现」。

## 禁止
- 不要输出泛泛的安全原则清单。
- 不要建议我引入大型安全框架来解决小问题。
````
