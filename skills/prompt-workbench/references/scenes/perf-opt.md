# 它太慢了，怎么优化

- **id**：`perf-opt`
- **分类**：开发
- **什么时候用**：页面加载慢、接口返回慢、数据一多就卡，但不知道瓶颈在哪。
- **关键词**：性能、优化、太慢、卡、加载慢、缓存、耗时、延迟

## 问题清单（按顺序，一次只问一个）

1. `symptom`（必填）：慢在哪？加载慢 / 点击后要等 / 查询慢 / 数据一多就卡。
   - 为什么问：不同慢法，瓶颈位置完全不同。
   - 示例回答：点「查询」后要等 4 秒才出结果，数据 1 万行时更慢
2. `numbers`（必填）：有具体数字吗？多慢、数据量多大、在什么设备上。
   - 为什么问：「很慢」不能优化，「4 秒」才能优化。
   - 示例回答：本机 4.2 秒，手机 8 秒；数据表 1 万行
3. `arch`（必填）：技术栈和链路是什么？请求打到哪、数据存在哪。
   - 为什么问：瓶颈可能在前端、网络、后端或数据库，链路决定从哪查。
   - 示例回答：浏览器 → Worker → D1 数据库，一次查询返回 1 万行
4. `constraint`（可选）：能改什么、不能改什么？（能加缓存吗、能改表结构吗、有预算吗）
   - 为什么问：有些优化要花钱或改架构，先定边界。
   - 示例回答：不能加付费服务，可以加缓存，表结构尽量不动

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位性能工程师。先教我测量，再谈优化；没有测量数据之前不要下结论。

## 现象
{{symptom}}

## 已有数字
{{numbers}}

## 技术链路
{{arch}}

## 约束
{{constraint}}

## 输出要求
1. **先测量**：给出 3 个具体测量动作（用什么工具、看哪个指标、预期看到什么），让我先拿到数据。
2. **瓶颈假设**：按可能性排序最多 3 个，每个给「怎么验证」和「如果是它会看到什么现象」。
3. **优化方案**：每个方案标注预期收益量级（毫秒/秒）和代价（改多少代码、有没有副作用）。
4. **优先级**：先做哪个，为什么（优先选能测量到收益、改动小的）。
5. 明确说明：哪些优化对当前场景**没必要做**，避免过度优化。

## 禁止
- 不要在没有测量数据的情况下断言瓶颈。
- 不要一上来就建议加缓存或换框架。
````
