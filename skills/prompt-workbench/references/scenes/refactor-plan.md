# 这段代码该重构了，给我一个计划

- **id**：`refactor-plan`
- **分类**：开发
- **什么时候用**：代码越改越难受、加个功能要动五个地方、或者想整理但不敢动。
- **关键词**：重构、refactor、解耦、技术债、拆分、整理代码、架构

## 问题清单（按顺序，一次只问一个）

1. `target`（必填）：要重构的是哪部分？文件/函数/模块，大概多少行。
   - 为什么问：重构范围决定风险，范围不清就没法排步骤。
   - 示例回答：app.js 里 300 行的渲染逻辑，现在一个函数干五件事
2. `pain`（必填）：现在最疼的是哪三件事？（具体到「每次改 X 都要动 Y」）
   - 为什么问：重构必须对准具体疼痛，否则就是纯改风格。
   - 示例回答：加一个字段要改 5 处 / 改样式经常漏掉导出逻辑
3. `scope`（必填）：哪些不能动？对外接口、数据库结构、必须保持的行为。
   - 为什么问：重构的边界越清楚，越敢动手。
   - 示例回答：接口返回结构不能变，测试必须一直保持全绿
4. `done`（必填）：怎么验证重构成功？能跑什么命令、点什么按钮。
   - 为什么问：没有验证方式的重构，等于赌博。
   - 示例回答：npm test 全绿 + 手动点一遍三条主流程
5. `constraint`（可选）：时间/技术约束？能不能引入新依赖、能不能暂停其他开发。
   - 为什么问：决定是「一步到位」还是「分十次小步走」。
   - 示例回答：两天内做完，不许加依赖

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位经历过多次线上事故的重构顾问。请给计划，不要给「全部重写」。

## 重构对象
{{target}}

## 现在的痛点
{{pain}}

## 不能动的边界
{{scope}}

## 成功标准
{{done}}

## 约束
{{constraint}}

## 输出要求
1. **现状诊断**：指出造成疼痛的结构性原因（最多 3 条），每条对应一个代码位置。
2. **分步计划**：拆成 3–6 步，每一步必须满足：
   - 单独可提交、可回滚
   - 做完这一步，测试仍然全绿
   - 说明这一步改动哪些文件、大约多少行
3. **风险**：哪一步最可能出问题，出问题时怎么判断、怎么回滚。
4. **不做的事**：明确列出这次不碰的部分。
5. 如果信息不足，先问我，不要假设我的代码结构。

## 禁止
- 不要提出「推倒重写」作为方案。
- 不要在没有测试覆盖的情况下建议大规模改动；如果有这种风险，先告诉我该怎么补测试。
````

## 交付要求

````text
## 通用交付规则（自动附加，优先级高于上面的表述）
- 如果我要的是「一个结果」（代码、程序、文案、方案、清单、报告）：**先给一版能直接用的最小版本**；缺的参数用默认假设填上并标注「假设」，不要因为信息不全就只问不产出。
- 如果我要的是「改我现有的仓库/文件/系统」：先列改动清单等我确认，再动手。
- 需要我补充的信息最多 3 条，放在结果之后，不要放在最前面。
````
