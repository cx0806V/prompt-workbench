# 帮我想测试用例

- **id**：`test-design`
- **分类**：开发
- **什么时候用**：功能写完了不知道怎么测，怕漏掉边界；或者要给别人的代码补测试。
- **关键词**：测试、用例、test、边界、验收、覆盖率、异常

## 问题清单（按顺序，一次只问一个）

1. `feature`（必填）：要测的是什么功能？输入是什么、输出应该是什么。
   - 为什么问：不知道输入输出，用例只能写成空话。
   - 示例回答：上传 CSV 并解析成表格，输入是文件，输出是行数组
2. `rules`（必填）：有哪些业务规则、限制、校验？比如长度限制、格式要求、必填项。
   - 为什么问：规则就是测试用例的来源。
   - 示例回答：文件 ≤ 5MB、必须是 UTF-8、必须有表头
3. `edge`（可选）：你最怕哪种情况出事？（空数据、超大输入、并发、网络失败……）
   - 为什么问：把恐惧变成用例，是最有效的补测方法。
   - 示例回答：文件里混了英文和中文，怕乱码
4. `stack`（可选）：当前测试环境？用什么框架、怎么跑。
   - 为什么问：决定用例写不写得出可执行的代码。
   - 示例回答：Node 自带 node:test，npm test 跑

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位擅长找边界条件的测试工程师。请设计测试用例，不要写空泛的「验证功能正常」。

## 被测功能
{{feature}}

## 业务规则与限制
{{rules}}

## 我最担心的场景
{{edge}}

## 测试环境
{{stack}}

## 输出要求
1. **用例表**：分三类列
   - 正常路径（Happy path）
   - 边界值（空、满、刚好超限、格式边界）
   - 异常路径（非法输入、依赖失败、超时）
   每条包含：编号 / 前置条件 / 输入 / 预期结果 / 优先级（P0/P1/P2）。
2. **最小可跑清单**：如果时间只够跑 5 条，跑哪 5 条，为什么。
3. **建议的断言写法**：针对最难的那 2 条用例，给出可执行的断言代码（用上面的测试环境）。
4. 指出我给的规则里**互相矛盾或缺失**的地方，不要替我补充假设。

## 禁止
- 不要写「测试系统稳定性」这类无法执行的用例。
- 不要为了凑数量编造不存在的业务规则。
````
