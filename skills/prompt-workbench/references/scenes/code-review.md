# 帮我审这段代码

- **id**：`code-review`
- **分类**：开发
- **什么时候用**：写完一段代码不确定质量，或者合并前想让人挑一遍问题。
- **关键词**：代码审查、review、code review、检查代码、合并、pr、质量

## 问题清单（按顺序，一次只问一个）

1. `code`（必填）：把要审的代码贴上来（或说明改动涉及哪几个文件）。
   - 为什么问：审查的对象必须是具体代码，不是描述。
   - 示例回答：贴 app.js 里 handleSubmit 那一段，约 40 行
2. `goal`（必填）：这段代码要做什么？一句话说清它的目的。
   - 为什么问：不知道目的，只能审出风格问题，审不出正确性问题。
   - 示例回答：把表单数据转成接口需要的格式并提交
3. `concern`（必填）：你最担心哪方面？正确性 / 安全 / 性能 / 可维护性 / 全部。
   - 为什么问：审查是有优先级的，全都要等于没重点。
   - 示例回答：安全和正确性，性能暂时不管
4. `standard`（可选）：有什么团队规范或技术约束？（语言版本、必须用的库、不许用的写法）
   - 为什么问：没有规范，AI 会按它的口味改你的风格。
   - 示例回答：用 ESM，不许新增依赖，函数不超过 50 行

## 模板（把 {{key}} 替换成用户回答原文）

````text
你是一位严格的代码审查者。按下面的优先级审，不要重写我的代码。

## 目的
{{goal}}

## 代码
{{code}}

## 我最关心
{{concern}}

## 规范约束
{{standard}}

## 输出要求
1. 先给一句总体判断：可以合并 / 改完再合并 / 建议重做。
2. 问题分三级列出，每条必须给「问题 → 为什么是问题 → 具体怎么改（可给关键片段，不要贴整段重写）」：
   - 🔴 必须改（正确性、安全、数据丢失风险）
   - 🟡 建议改（可维护性、可读性、边界处理）
   - ⚪ 不用改（风格偏好，说明为什么不影响）
3. 指出 1 个我可能没意识到、但值得知道的问题（比如隐含假设、并发、时区、编码）。
4. 如果代码里信息不足，直接问我，不要假设。

## 禁止
- 不要因为「可以更优雅」就要求重写。
- 不要一次列出超过 10 条问题，优先挑真正重要的。
````
